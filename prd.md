Problem StatementsStatus quo manajemen operasional pada Sanggar Happy Drawing saat ini masih mengandalkan proses manual yang terfragmentasi. Pendaftaran siswa baru dilakukan melalui formulir fisik atau pesan instan yang tidak terstruktur, sementara pencatatan administrasi keuangan dan absensi tersebar di berbagai buku besar atau file spreadsheet lokal yang tidak sinkron. Kondisi ini menyebabkan manajemen kesulitan dalam memantau data secara *real-time* dan sering terjadi inkonsistensi data antara jumlah siswa aktif dengan laporan keuangan yang masuk.Dampak negatif dari inefisiensi ini sangat signifikan terhadap skalabilitas sanggar. Penumpukan data pendaftaran yang tidak terverifikasi mengakibatkan keterlambatan dalam memulai kelas bagi siswa baru. Dari sisi keuangan, tidak adanya sistem notifikasi otomatis dan riwayat transaksi yang transparan membuat proses penagihan infak bulanan sering terlewat, yang pada akhirnya mengganggu arus kas operasional sanggar. Selain itu, karya-karya kreatif siswa tidak terdokumentasi dengan baik secara digital, sehingga potensi pemasaran sanggar melalui portofolio siswa menjadi tidak optimal.Solusi yang ditawarkan adalah pengembangan aplikasi web "Happy Drawing" sebagai Sistem Informasi Manajemen Sanggar (SIMS) yang terpusat. Aplikasi ini mengintegrasikan portal publik untuk pendaftaran, portal siswa untuk memantau progres dan pembayaran, serta panel administrasi untuk kendali operasional penuh. Dengan memanfaatkan Google Apps Script sebagai *backend* dan Google Sheets sebagai *database*, solusi ini memberikan kemudahan aksesibilitas tanpa beban biaya infrastruktur server yang tinggi, namun tetap menjamin integritas data melalui validasi sistemik.Nilai tambah utama dari Happy Drawing terletak pada pendekatan *mobile-first responsive design* yang memastikan orang tua siswa dapat melakukan transaksi dan melihat galeri karya anak mereka langsung dari perangkat seluler. Diferensiasi produk ini diperkuat dengan fitur otomatisasi pembuatan ID Siswa berbasis tanggal lahir dan urutan pendaftaran, serta sistem moderasi galeri karya yang memungkinkan sanggar membangun komunitas kreatif digital. Integrasi laporan keuangan otomatis memberikan transparansi penuh bagi manajemen untuk mengambil keputusan strategis berdasarkan data yang akurat.# 2\. User Flow### 5.1 Alur Utama: Pendaftaran hingga Aktivasi Akun (Happy Path)1. **Action Name:** Akses Portal Publik. Calon siswa membuka website.2. **Action Name:** Isi Form Pendaftaran. Input data pribadi, pilih kelas, upload foto, buat password.3. **Decision Point:** Validasi Input. Jika data tidak lengkap, sistem menampilkan error. Jika lengkap, lanjut.4. **Output:** Data tersimpan di Sheet DAFTAR dengan status PENDING.5. **Action Name:** Verifikasi Admin. Admin memeriksa data di Panel Pendaftaran.6. **Action Name:** Approve Pendaftaran. Admin menekan tombol "Setujui".7. **Output:** Sistem men-generate ID Siswa unik, memindahkan data ke Sheet BIODATA \& USER, status menjadi AKTIF.8. **Action Name:** Login Siswa. Siswa login menggunakan kredensial yang didaftarkan.### 5.2 Alur Alternatif: Pembayaran Infak Ditolak1. **Action Name:** Upload Bukti Bayar. Siswa mengunggah foto transfer di Portal Siswa.2. **Output:** Transaksi muncul di Panel Pembayaran Admin (Status: PENDING).3. **Action Name:** Review Admin. Admin melihat bukti transfer buram atau nominal tidak sesuai.4. **Action Name:** Reject Pembayaran. Admin menekan "Tolak" dan mengisi alasan (misal: "Foto bukti tidak terbaca").5. **Output:** Status di portal siswa berubah menjadi DITOLAK, muncul notifikasi beserta alasan admin.6. **Action Name:** Re-upload. Siswa mengunggah kembali bukti yang benar.# 6\. Non-Functional Requirements* **UX/Design:**  * Menggunakan tema Glassmorphism dengan *backdrop-filter blur*.  * Animasi transisi antar halaman menggunakan AOS Library.  * Responsivitas penuh (Bootstrap 5 Grid) untuk Desktop (1200px+), Tablet (768px), dan Mobile (480px).  * Notifikasi interaktif menggunakan SweetAlert2 (Toast \& Modal).  * *Bottom Navigation* khusus untuk tampilan mobile agar menyerupai aplikasi native.* **Performance:**  * Waktu muat halaman awal (First Contentful Paint) < 2 detik.  * Latensi pemanggilan API Google Apps Script < 3 detik untuk operasi standar.  * Implementasi *Background Sync* setiap 5 menit untuk menjaga aktualitas data.* **Security:**  * Hashing password menggunakan algoritma SHA-256 di sisi server.  * Proteksi akses API melalui validasi session di setiap fungsi backend.  * Implementasi *Soft Delete* (kolom IS\_DELETED) untuk mencegah kehilangan data permanen.* **Compatibility:**  * Mendukung peramban modern (Chrome, Safari, Edge, Firefox).  * Optimal pada sistem operasi Android dan iOS.* **Technical Constraints:**  * Limitasi kuota harian Google Apps Script (URL Fetch, Email, Trigger).  * Batas sel Google Sheets (maksimal 10 juta sel).  * Keterbatasan eksekusi skrip maksimal 6 menit per *request*.# 8\.
